# 40. 발표 대본

> 시연 준비: MySQL 켜기 → Eclipse Tomcat 실행 → 브라우저 탭 미리 열기
> ① 메인 ② `custom?pick=1,2&days=30` ③ 로그인 화면 ④ 관리자 주문 화면 (admin 으로 다른 브라우저/시크릿 창)

---

## 5분 버전

**[0:00 소개 — 30초]**
안녕하세요, 커스텀 영양제 쇼핑몰 **필살기**를 만든 팀입니다. 영양제를 하루 1포 단위로 팔고, 손님이 직접 조합을 짜면 함께 먹으면 안 되는 조합을 바로 알려 주는 쇼핑몰입니다.

**[0:30 구조 — 1분]**
JSP · 서블릿 MVC 구조입니다. 모든 요청은 `BaseServlet` 이 먼저 받아 로그인과 역할을 검사하고, 기능 서블릿이 규칙을 확인한 뒤 DAO 가 SQL 을 실행합니다. 결과는 모델 객체에 담겨 JSP 로 그려집니다. DB 는 MySQL 테이블 22개이고, Tomcat 커넥션 풀로 연결합니다. 역할은 구매하는 USER 와 관리하는 ADMIN 두 가지로 완전히 나눴습니다.

**[1:30 시연 ① 조합 맞추기 — 1분]**
(조합 화면) 종합비타민과 비타민A 를 고르면 바로 "비타민A 과다 섭취" 경고가 뜹니다. 금지 조합은 DB 테이블에 쌍으로 저장돼 있어서 관리자가 화면에서 추가할 수 있습니다. 일수를 7일로 바꾸면 합계와 배송비가 즉시 바뀌고, 주소창도 바뀌어 이 링크를 그대로 공유할 수 있습니다.

**[2:30 시연 ② 주문 — 1분]**
(hong 로그인 → 상품 상세 14일 담기 → 장바구니 → 주문) 결제는 주문, 주문 상품, 재고 차감, 결제, 배송, 장바구니 비우기를 **한 트랜잭션**으로 처리합니다. 재고 차감은 `stock >= 수량` 조건을 건 UPDATE 라서 동시에 주문해도 재고가 음수가 되지 않고, 하나라도 실패하면 전부 되돌립니다.

**[3:30 AI 와 마무리 — 1분 30초]**
상품 상세의 설명 · 리뷰 요약은 학교 GPU 서버의 LLM 이 만듭니다. AI 응답이 수십 초 걸리기 때문에 화면을 그릴 때는 부르지 않고, 백그라운드 스레드가 미리 만들어 DB 에 저장합니다.
마지막으로, 제출 전에 코드를 단순화하면서 원본과 수정본을 나란히 띄워 117개 화면과 Playwright 테스트 12개로 **동작이 하나도 바뀌지 않았음을 확인**했습니다. 감사합니다.

## 10분 버전

**[0:00 소개 — 1분]**
(5분 버전 소개 +) 판매 단위가 1포라서 장바구니 수량이 곧 섭취 일수입니다. 낱개 38종과, 낱개를 미리 묶은 트랙 패키지 11종이 있습니다.

**[1:00 구조 — 2분]**
- 화면 흐름 그림(`01-architecture.md` 의 mermaid)을 보여 주며: 브라우저 → BaseServlet → 기능 서블릿 → DAO → DB → JSP.
- `BaseServlet` 이 입장 검사: 점검 모드, `/admin` 은 ADMIN, 구매 경로는 USER. 화면에서 버튼을 숨기는 건 편의, 진짜 차단은 서버.
- 서블릿은 정확한 주소만 매핑 — 와일드카드를 쓰면 JSP 폴더와 겹쳐 무한 순환이 생기기 때문.
- `DB.java` 하나가 커넥션 풀, 결과를 객체로 바꾸기, 트랜잭션(ThreadLocal)을 맡아 DAO 코드가 SQL 한 줄 수준으로 짧다.

**[3:00 DB — 1분 30초]**
- 테이블 22개, 뷰 5개. 주문 상품은 주문 당시 이름 · 가격을 복사(스냅샷)해서 나중에 가격이 바뀌어도 내역은 그대로.
- 금지 조합은 `product_a < product_b` CHECK 로 한 방향만 저장. 배송중 이상은 운송장이 없으면 DB 가 거부.
- 배송비 · 무료배송 기준 · 점검 모드 같은 값은 `system_config` 테이블에서 읽어 코드 수정 없이 바뀐다.

**[4:30 시연 ① 조합 맞추기 + 경고 — 1분 30초]**
(5분 버전 ① +) 트랙 두 개에 같은 영양제가 들어 있으면 "중복 섭취"도 알려 줍니다. 같은 경고 로직(`ConflictDAO.warnings`)을 장바구니 · 상세 · 조합 화면이 함께 씁니다.

**[6:00 시연 ② 주문 · 배송 — 1분 30초]**
(5분 버전 ② +) 관리자 화면에서 배송을 한 단계씩 넘깁니다. `WHERE status = 직전 단계` 조건이라 두 번 눌러도 한 번만 넘어가고, 넘길 때마다 배송 이력과 관리자 로그가 남습니다. 손님 주문 상세의 배송 타임라인이 그 이력입니다.

**[7:30 AI — 1분]**
- 요약: 저장형. 원본의 해시를 같이 저장해 원본이 바뀌면 다시 만든다. 백그라운드 스레드 1개가 순서대로 처리.
- 검색 추천: 검색어마다 달라 미리 못 만드니까, 페이지를 먼저 보여 주고 JS 가 비동기로 요청. 같은 검색어는 메모리 캐시.
- AI 서버가 꺼져도 쇼핑몰은 정상 동작.

**[8:30 단순화와 검증 — 1분]**
(`20-simplify.md` 의 예시 1개 + 검증 표) 줄 수를 줄이는 것보다 중복을 없애는 게 목표였고, 원본과 수정본을 나란히 띄워 HTML · CSS · JS · E2E 테스트로 같음을 확인했습니다. 찾은 기존 버그는 섞지 않고 따로 기록했습니다.

**[9:30 한계와 마무리 — 30초]**
비밀번호 해시 미적용, 모의 결제 같은 한계는 알고 있고 개선 방향도 정리했습니다. 감사합니다.
