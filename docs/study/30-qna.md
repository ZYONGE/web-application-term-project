# 30. 발표 예상 질문과 답변

## 구조 · 설계

**Q. MVC 를 어떻게 나눴나요?**
A. 서블릿(`shop.service`)이 컨트롤러로 검사와 업무 규칙, 트랜잭션을 맡고, DAO(`shop.dao`)가 SQL 만, JSP 는 JSTL 로 그리기만 합니다. JSP 에 스크립틀릿과 DB 접근이 없습니다.

**Q. 로그인 체크를 서블릿마다 하나요?**
A. 아니요. 모든 서블릿이 `BaseServlet` 을 상속하고, `doGet` · `doPost` 에서 `allowed()` 를 먼저 거칩니다. 경로가 `/admin` 이면 ADMIN, `/cart · /order · /mypage · /wish` 면 USER 만 통과합니다. 화면에서 버튼을 숨기는 건 편의이고 진짜 차단은 서버입니다.

**Q. 왜 `/cart/*` 같은 와일드카드 매핑을 안 썼나요?**
A. JSP 폴더 이름과 URL 앞부분이 같아서, 서블릿이 `cart/list.jsp` 로 forward 하면 다시 `/cart/*` 서블릿이 잡는 무한 순환이 생깁니다. 그래서 정확한 주소만 매핑했습니다.

**Q. DB 연결은 어떻게 관리하나요?**
A. Tomcat JNDI 커넥션 풀(`jdbc/shop`, commons-dbcp)을 씁니다. 접속 정보는 `context.xml` 에만 있고 git 에서 제외했습니다. `DB.java` 가 커넥션을 빌려 쓰고 바로 반납합니다.

## 트랜잭션 · 동시성

**Q. 결제 중간에 오류가 나면요?**
A. 주문 · 주문상품 · 재고 차감 · 결제 · 배송 · 장바구니 비우기가 한 트랜잭션입니다. `DB.begin()` 후 `finally` 에서 `DB.end()` 를 부르는데, commit 하지 않았으면 rollback 합니다. 그래서 중간 실패 시 아무것도 남지 않습니다.

**Q. 두 사람이 마지막 재고를 동시에 사면요?**
A. `UPDATE product SET stock = stock - ? WHERE product_id = ? AND stock >= ?` 로 조건과 차감을 한 문장에서 합니다. 늦은 쪽은 0행이 바뀌어 Fail 이 나고 전체 rollback 됩니다. 재고가 음수가 되지 않습니다.

**Q. 관리자 두 명이 동시에 "배송 다음 단계"를 누르면?**
A. `UPDATE delivery … WHERE delivery_id = ? AND status = <직전 단계>` 라서 먼저 누른 쪽만 성공하고, 뒤쪽은 0행 → "이미 바뀌었습니다" 안내 후 rollback 합니다.

**Q. 트랜잭션 안에서 DAO 들이 어떻게 같은 커넥션을 쓰나요?**
A. `DB.begin()` 이 커넥션을 `ThreadLocal` 에 넣어 두고, 그 스레드의 DAO 호출은 그 커넥션을 꺼내 씁니다. 요청 하나 = 스레드 하나라서 다른 요청과 섞이지 않습니다.

## 보안

**Q. SQL 인젝션은?**
A. 모든 값은 `PreparedStatement` 의 `?` 로 바인딩합니다. 정렬처럼 SQL 구조가 바뀌는 부분은 사용자 값을 넣지 않고, 정해진 ORDER BY 문 중 하나를 고르는 방식입니다.

**Q. XSS 는?**
A. 사용자 입력은 `<c:out>` 으로 이스케이프해서 출력합니다.

**Q. 비밀번호는 암호화하나요?**
A. (솔직하게) 아니요, 수업 범위에서 평문으로 저장 · 비교합니다. 실서비스라면 BCrypt 같은 단방향 해시와 솔트를 써야 합니다. 로그인할 때 세션을 새로 만들어(`invalidate`) 세션 고정 공격은 막았습니다.

**Q. 로그인 후 돌아가는 주소(returnUrl)를 악용할 수 있나요?**
A. 로그인은 우리 사이트 주소(`컨텍스트경로/`로 시작)이고 그 역할이 갈 수 있는 곳일 때만 돌아갑니다. 다만 다른 화면의 `back` 파라미터는 `//` 로 시작하는 주소를 막지 않는 부분이 있어, 개선 대상으로 기록해 두었습니다.

## 기능

**Q. 동시 섭취 경고는 어떻게 판단하나요?**
A. 고른 상품을 트랙은 구성품으로 펼쳐 낱개 id 집합을 만들고, `supplement_conflict` 테이블에 있는 쌍이 그 안에 둘 다 있으면 "동시 섭취 주의", 같은 낱개가 두 번 이상이면 "중복 섭취"로 알립니다. 규칙이 데이터라서 관리자가 화면에서 추가할 수 있습니다.

**Q. 상품 가격이 바뀌면 지난 주문은?**
A. `order_item` 에 주문 당시 이름 · 가격 · 트랙 구성을 복사해 두기 때문에 바뀌지 않습니다.

**Q. AI 는 느린데 페이지가 안 멈추나요?**
A. 화면을 그릴 때 AI 를 부르지 않습니다. 요약은 백그라운드 스레드(`LlmWorker`)가 만들어 DB 에 저장하고 화면은 저장된 것만 읽습니다. 원본이 바뀌었는지는 해시(`source_key`)로 판단합니다. 검색어별 추천은 페이지를 먼저 그리고 JS 가 비동기로 요청합니다. AI 서버가 꺼져 있어도 쇼핑몰은 정상입니다.

**Q. 결제는 실제로 되나요?**
A. 모의 결제입니다. 과제 규칙상 실결제 · 외부 API 는 금지였고, 결제 · 환불 상태와 금액만 DB 에 기록합니다.

## 단순화 · 테스트

**Q. 리팩터링 후 동작이 같다는 걸 어떻게 아나요?**
A. 원본과 수정본을 Tomcat 하나에 나란히 띄워 117개 화면의 HTML, 82개 화면 · 폭 조합의 계산된 CSS, 27단계 JS 조작 결과를 비교해 모두 같았고, Playwright 테스트 12개가 양쪽에서 모두 통과했습니다.

**Q. 줄 수가 별로 안 줄었는데 단순화가 맞나요?**
A. 목표가 줄 수가 아니라 중복 제거와 읽기 쉬움이었습니다. 같은 로직을 여러 곳에 복사하던 걸 한 메서드로 모았고, 중첩 삼항을 if 로 풀면서 오히려 줄이 늘어난 곳도 있습니다.
