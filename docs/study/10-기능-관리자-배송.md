# 10. 기능 — 관리자 · 배송 단계 관리

## 핵심

관리자는 상품 · 주문 · 회원 · 게시판을 관리하고, **모든 조작을 `admin_log` 에 남긴다**. 배송은 **한 번에 한 단계씩만** 넘어간다.

## 관리자 화면 9개

| URL | 서블릿 | 하는 일 |
|---|---|---|
| `/admin/dashboard` | AdminServlet | 일별 매출 · 배송 단계별 건수 · 재고 부족 (뷰 3개 사용) |
| `/admin/orders` | AdminServlet | 주문 검색 · 상세 · **배송 다음 단계** · 취소 |
| `/admin/members` | AdminServlet | 회원 검색 · 탈퇴 처리 |
| `/admin/notices` · `/admin/qna` · `/admin/reviews` | AdminServlet | 공지 등록 · 수정 · 삭제, 문의 답변, 리뷰 삭제 |
| `/admin/products` | AdminProductServlet | 상품 등록 · 수정(이미지 업로드, 트랙 구성), 숨김, AI 요약 전체 생성 |
| `/admin/categories` · `/admin/conflicts` | AdminProductServlet | 카테고리, 금지 조합 관리 |

## 배송 다음 단계 — `AdminServlet.nextStep()`

```
결제완료 → 상품준비 → 배송중 → 배송완료      (OrderDAO.FLOW 배열)

1. 지금 단계(from) 읽기 → 다음 단계(to) = FLOW[step + 1]
2. to 가 "배송중"이면 택배사 · 운송장 필수 (없으면 Fail)
3. DB.begin()
4. UPDATE delivery SET status = to, <단계 시각> = NOW() WHERE delivery_id = ? AND status = from
     → 0행이면 "배송 상태가 이미 바뀌었습니다" (다른 관리자가 먼저 눌렀거나 두 번 클릭)
5. delivery_history 에 from → to 기록
6. admin_log 기록 (배송중이면 운송장 기록 한 줄 더)
7. commit
```

- `WHERE status = from` 이 핵심: **조건부 UPDATE 로 낙관적 잠금**과 같은 효과.
- DB 에도 CHECK 가 있어 배송중 · 배송완료인데 운송장이 없으면 DB 가 거부한다 (코드 실수 방어).
- 회원 쪽 주문 상세의 **배송 타임라인**은 이 `delivery_history` 를 그대로 보여 준다.

## 상품 등록 (이미지 업로드)

- `<form enctype="multipart/form-data">` → `cos.jar` 의 `MultipartRequest` 로 받아 `WebContents/upload/` 에 저장, DB 에는 `/upload/파일명` 경로만.
- 트랙 상품이면 구성 낱개 목록(`track_item`)도 함께 저장.

## admin_log

`AdminDAO.adminLog(관리자id, 동작, 대상 테이블, 대상 id, 설명)` — 예: `DELIVERY_NEXT_STEP`, `ORDER_CANCEL`, `QNA_ANSWER`, `REVIEW_DELETE`, `CONFLICT_CREATE`. 누가 언제 무엇을 바꿨는지 추적.
